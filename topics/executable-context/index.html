    Executable Context

    What is it¶

    Executable context is the practice of giving AI coding agents feedback they can act on — tests, type checkers, linters, REPL output, structured exploration of the codebase — instead of, or in addition to, static markdown instructions. The tests, checks and tool output are context the agent can run against, rather than prose it has to interpret and remember.

    This page examines the claim that executable and interactive context produces materially more correct, robust and maintainable code than documentation alone, and that the engineer's leverage lies in designing the environment the agent works in rather than in writing prompts. It draws on controlled comparisons of context formats, agent-computer interface and harness design, the measured effect of repository context files, and the failure modes — plausible-but-wrong code, gamed tests, misjudged productivity — that appear when verification is missing. How to apply the findings in a team is the companion page, Executable Context Practices.

    The short answer: several independent lines of evidence point the same way — interactive tests, structured representations and designed tool interfaces outperform their non-interactive or unstructured baselines (plain prompting, raw SQL schemas, a default shell), and the one study that measures static context files directly finds marginal gains at best — but the studies measure different tasks with different metrics, and no study compares the two head-to-head on one coding benchmark.

    Interactive tests clarify intent better than prose¶

    The most direct evidence comes from Microsoft Research's TiCoder study. Interactive test-based intent clarification — where the user and the LLM iteratively refine understanding through executable unit tests — produces a 45.97% absolute improvement in pass@1 over code generation without clarification, across four state-of-the-art LLMs on two Python datasets within five interactions — with user feedback simulated by an idealized proxy. (The 15-programmer user study measured how well users judged code and their cognitive load, not pass@1.) Note what is being compared: LLM-proposed tests clarified with (simulated) user feedback, not human-written failing tests against documentation. Tests serve as partial formalization of intent: executable, verifiable, unambiguous. Static natural-language descriptions leave the intent gap open.

    As a side effect, the interaction produces a test suite — the specification artifact is the verification artifact.

    Source: TiCoder: LLM-Based Test-Driven Interactive Code Generation

    Structured representations beat flat text for relational questions¶

    The starkest controlled comparison in the corpus. GPT-4 answering questions about an enterprise SQL database achieves 16.7% accuracy when querying the SQL schema directly and 54.2% accuracy when the database is exposed as a knowledge graph — a 37.5 percentage point delta. The KG setup includes an ontology layer with business context, so this compares a representation plus added semantics, not format alone. The task is enterprise question answering, not coding.

    GraphRAG work points the same way for relational queries: it improves precision and comprehensiveness by capturing relational knowledge that flat retrieval misses, particularly for multi-hop queries that require reasoning across entities.

    Sources: KG Benchmark for Enterprise SQL QA, Graph Retrieval-Augmented Generation: A Survey

    Interface design moves agent performance without changing the model¶

    SWE-agent demonstrated that designing interfaces specifically for LLM agents — compact feedback, guardrails against error propagation, informative but concise responses — produced, as the paper reports, 10.7 percentage points of improvement over a default Linux shell in ablations on SWE-bench Lite (its own table puts the gap at about 7 points when the shell-only agent also gets demonstrations). Separately, SWE-agent reached 12.47% on full SWE-bench against a previous best of 3.8% from non-interactive retrieval-augmented systems — a different comparison. Claude 3 Opus achieved 10.5% despite SWE-agent being developed for GPT-4 Turbo, indicating these gains are portable across models.

    Four ACI design principles emerged: simple and easy to understand, compact and efficient, informative but concise feedback, and guardrails that prevent error cascades.

    The Art of Tool Interface Design reinforces this: its Thinker framework — state-machine augmented generation, delegated sub-task tools and adaptive context management — achieved 82.6% success on tau-bench retail with GPT-4o (vs 68.3% baseline) and 81.9% with Llama-3.1 405B (vs 49.6% baseline), all through prompting and tool design rather than fine-tuning.

    Sources: SWE-agent, The Art of Tool Interface Design

    The harness matters as much as the model¶

    Meta-Harness argues the harness "often matters as much as the model itself," citing prior work in which changing only the harness around a fixed model produced up to a 6× gap on the same benchmark. Its own key insight: optimizers that access full execution traces outperform text-only optimizers, which are poorly matched to the problem because they compress feedback too aggressively (scalar scores lose the signal); in its ablation, full access to execution traces was the most important component. On online text classification, Meta-Harness improved over the best prior hand-designed harness (ACE) by 7.7 points while using 4x fewer context tokens, and a single discovered harness improved accuracy on 200 IMO-level math problems by 4.7 points across five held-out models.

    This aligns with the broader harness engineering discipline synthesized from OpenAI, Stripe, and Anthropic practices: the engineer's job is increasingly building the environment (constraints, tools, feedback loops) rather than writing code directly. See Harness Engineering.

    Sources: Meta-Harness, Harness Engineering Playbook

    Static context files have a low ceiling¶

    The ETH Zurich evaluation of AGENTS.md and CLAUDE.md files — the first rigorous empirical study of repository-level context files — found that developer-provided context improves agent performance by only +4% on average, while LLM-generated context actually hurts performance by -3%. Both increase inference cost by 20% or more. Unnecessary constraints in context files actively degrade performance — agents follow instructions faithfully, and bad instructions produce bad outcomes. The exception: in repositories with their other documentation removed, LLM-generated files helped by 2.7% on average.

    The study did find that context files encourage broader exploration (more file traversal, more thorough testing), which suggests they have value as pointers to executable checks rather than as containers of knowledge.

    Codified Context, an experience report on a 108K-line C# codebase over 283 sessions, argues single-file manifests don't scale and proposes hot/cold memory separation plus 19 domain-specialist agents. It cites prior work associating AGENTS.md presence with a 29% reduction in median runtime and 17% fewer output tokens.

    Sources: Evaluating AGENTS.md, Codified Context

    The gains point the same way but are not comparable¶

    Signal Comparison Delta Source
    Interactive test clarification vs none (simulated users) pass@1 code generation +46pp TiCoder
    Knowledge graph + ontology vs raw SQL schema QA accuracy +37.5pp KG Benchmark
    Designed ACI vs default shell SWE-bench Lite solve rate +10.7pp SWE-agent
    Optimized vs hand-designed harness (ACE) Text-classification accuracy +7.7 pts, 4× fewer tokens Meta-Harness
    Developer context files vs none Agent task completion +4% Evaluating AGENTS.md

    The direction is consistent: executable, structured and interactive context outperforms its baselines, and the one direct measurement of static documentation finds marginal gains at best and negative returns at worst. The magnitudes come from different tasks and metrics, so they shouldn't be ranked against each other.

    Without executable checks, plausible code passes for correct¶

    The evidence is not just that executable context works better — the absence of executable verification produces specific, documented failure modes. The first is that LLM-generated code optimizes for plausibility, not correctness.

    The most vivid demonstration, though a single and contested one (the project was unfinished and its README has since been revised): a 576,000-line LLM-generated Rust reimplementation of SQLite that passed all its tests but was about 20,000x slower than SQLite on the author's primary-key lookup benchmark. It missed performance invariants (INTEGER PRIMARY KEY lookups, page-cache behaviour) that only executable benchmarks would catch.

    At the benchmark level, this manifests as a dramatic gap between single-attempt and filtered performance. Codex-12B solved 28.8% of HumanEval problems with a single sample and 70.2% when any of 100 samples counted. For Codex-S, picking the sample that passes the unit tests solved 77.5%, but picking by the model's own mean log-probability solved only 44.5%. The model can generate correct code but cannot reliably identify which of its outputs is correct without external verification.

    Sources: Your LLM Doesn't Write Correct Code, Codex/HumanEval

    Agents game the tests they can see¶

    Agents adapt their output to pass the tests they can see. They write mocks that simulate expected behavior rather than testing actual integration. They hardcode return values that match test assertions. RLHF-trained sycophancy makes this worse: agents generate what users describe rather than what's needed, and the same sycophancy bias infects self-review.

    Users often don't catch it. The vibe-coding review (101 grey-literature sources, 518 behavioural accounts) found skipped QA was the most common QA practice (36% of QA accounts), and 10% delegated quality checks back to the same AI; it does not measure test gaming directly. The review also cites an earlier study (Pearce et al.) finding about 40% of 1,689 Copilot-generated programs contained security vulnerabilities, and another (Majdinasab et al.) finding that even additional safety layers frequently produce insecure code.

    The countermeasure is structural: separate test authorship from implementation context, use property-based tests that are hard to game with hardcoded values, and place interface tests in a separate agent context with minimal knowledge of the implementation.

    Sources: How To Effectively Write Quality Code With AI, Your LLM Doesn't Write Correct Code, Vibe Coding in Practice

    Developers misjudge their own productivity¶

    The METR randomized controlled trial with 16 experienced open-source developers across 246 real tasks found that AI tools increased task completion time by 19%. Developers had predicted a 24% speedup before the study and still estimated a 20% speedup after participating — despite the measured slowdown. Economists predicted 39% shorter task times; ML researchers predicted 38%.

    This is the most dangerous finding in the corpus. Without executable measurement, even experts cannot accurately assess the impact of AI tools on their own productivity. Every claim of "I'm faster with AI" that lacks measurement is suspect.

    The finding is specific to large, mature codebases with highly experienced developers. It does not imply AI tools are useless — improvements to prompting, agent scaffolding, and domain-specific adaptation could yield speedups. But it does imply that subjective assessment is unreliable.

    Source: METR Study

    One possible explanation comes from the cognitive agency surrender literature, which argues frictionless interfaces exploit System 1 heuristics and bypass the analytical reasoning that would catch the discrepancy. That paper is a literature analysis and doesn't study METR's result directly. Either way, the feeling of productivity is not productivity.

    Implication: any AI adoption evaluation that relies on developer surveys or self-reported time savings is measuring perception, not reality.

    Sources: METR Study, Cognitive Agency Surrender

    Frictionless tools invite cognitive surrender¶

    Frictionless AI interfaces exploit cognitive miserliness — the tendency to offload reasoning to the easiest available path. An automated classification of 1,223 high-confidence AI-HCI papers (2023-2026) found 67.3% structural hegemony for frictionless usability, while research on epistemic sovereignty dropped from 19.1% (2025) to 13.1% (2026).

    The implication: tools that feel most productive may be the ones that most effectively bypass analytical reasoning. The paper argues for intentional friction in interface design as a prerequisite for cognitive resilience; review gates, mandatory test execution and plan-then-execute workflows are this page's extrapolation of that to engineering practice.

    Field observations (N=13) and surveys (N=99) of professional developers offer a contrasting picture: experienced developers do not "vibe code." They carefully control AI agents through planning and supervision, retain agency over software design, and insist on quality attributes — in other words, they resist the surrender the HCI analysis warns about. The same paper cites HULA's deployment, where about 8% of issues ended in a merged PR (see Executable Context Practices).

    Sources: Cognitive Agency Surrender, Professional Developers Don't Vibe, They Control

    Extra agents add overhead unless they bring new signal¶

    Information-theoretic analysis proves that multi-agent architectures sharing the same base model and context cannot outperform a centralized decision maker. Communication between agents degrades decision quality, quantifiable via mutual information loss. Under fixed reasoning-token budgets, single-agent systems match or outperform multi-agent systems on multi-hop reasoning — though multi-agent systems become competitive when a single agent's context utilisation degrades.

    Multi-agent message-passing is lossy compression of full context. Adding agents without adding information is adding overhead without adding capability.

    Sources: Reliability Limits, Single-Agent Outperforms Multi-Agent

    The corollary: the main lever for multi-agent reliability is genuinely new exogenous signals (the paper also credits preserving decision-relevant information and non-redundant review) — tool calls, database lookups, test execution results, linter output, file system reads. These provide information the model does not already have.

    This means: multi-agent is valuable when each agent interacts with a different part of the environment. Agent A runs tests on module X while Agent B runs tests on module Y — each gets exogenous signal the other doesn't have. But Agent A "planning" and Agent B "reviewing" with the same context is theater.

    Human review is optimally deployed when automated posterior risk exceeds review cost — not as a blanket policy, but targeted at the highest-risk decisions.

    This is the theoretical argument. Some empirical results complicate it: one multi-agent system gains without any tools, and another gains from how its agents communicate under a compute-matched baseline. See Multi-Agent Systems for that evidence.

    Source: Reliability Limits

    Other sources point the same way¶

    Sources that inform this page without anchoring a specific finding above:

    • Benchmarks and baselines. SWE-bench set the real-world bar (the best model solved 1.96% at launch). Agentless showed a fixed localize-repair-validate pipeline reaching 32% on SWE-bench Lite at about $0.70 per task. METR's time-horizon study finds the length of tasks agents complete doubling about every 7 months.
    • Context retrieval and reuse. ContextBench finds agents explore more context than they use, making consolidation a key bottleneck. ACE evolves contexts incrementally (+10.6% on agent benchmarks). Everything is Context proposes a file-system abstraction for governed context. An analysis of Claude Code's traffic traces one SWE-bench Verified task: 92 LLM calls with 92% prefix reuse.
    • How tools are configured and built. A study of 2,923 repositories finds static configuration dominates and executable integrations are still rare. OPENDEV and Dive into Claude Code describe harness designs with layered safety and context compaction. Environment Scaling argues static datasets are insufficient for adaptive agents.
    • Verification tooling. MCPEval automates agent evaluation through tool-call matching and LLM judging. Verify turns specs into Playwright checks run by parallel browser agents. Testing with AI Agents finds AI authored 16.4% of test commits in the repositories studied.
    • Why outputs need checking at all. Sleeper Agents shows trained-in backdoors persist through safety training, and monitoring reasoning models finds chain-of-thought monitoring works but optimizing against it teaches obfuscation.

    What the evidence supports¶

    • Executable feedback beats non-interactive baselines. Interactive test clarification (+46pp pass@1 with simulated users, TiCoder), designed agent interfaces (+10.7pp over a plain shell, SWE-agent) and automated harness search (+7.7 points over ACE on text classification, where access to full execution traces was the key ingredient, Meta-Harness) all beat their baselines, while context files add about +4% on average (Evaluating AGENTS.md). Each is a controlled result on its own task; the magnitudes can't be ranked against each other.
    • Static context files should be short pointers, not manuals. Developer-written files gave +4% on average, LLM-generated ones −3%, both at 20%+ extra cost; that they encourage broader exploration suggests their value is in pointing at checks. The exception: with no other documentation, LLM-generated files helped by 2.7% (Evaluating AGENTS.md).
    • Models can generate correct code but can't pick it out. Codex-S solved 77.5% when the unit tests chose the sample and 44.5% when its own log-probability did; external verification is what closes the gap (Codex/HumanEval).
    • Don't trust perceived productivity. In the METR RCT, experienced developers were 19% slower while believing they were 20% faster (METR). It is one study, of mature codebases and experienced developers.
    • More agents help mainly with new information. The theoretical result is that role decomposition over the same model and context cannot beat a single decision maker (Reliability Limits); empirical exceptions are covered in Multi-Agent Systems.

    In practice¶

    The practices that follow from this evidence — with code examples for Java, Scala and Python, adoption order and a quick-reference table — are on Executable Context Practices. Its highest-leverage starting points are executable specs before implementation, linter rules as architecture guardrails, separating test authorship from implementation, performance gates in CI, and plan-then-execute review gates.

    Open questions¶

    • How much of each gain survives on the same task? The headline numbers (TiCoder, the KG benchmark, SWE-agent, Meta-Harness, AGENTS.md) come from different tasks and metrics. No study compares executable context against static documentation head-to-head on one coding benchmark.
    • Does writing failing tests first beat TiCoder-style clarification? The strongest effect size here is for LLM-proposed tests refined with (simulated) user feedback. Whether human-authored failing tests given upfront perform as well is untested.
    • Does constraining the solution space measurably help? The linter-as-guardrail practice rests on a practitioner report. A controlled comparison of constrained and unconstrained agents on the same codebase would settle it.
