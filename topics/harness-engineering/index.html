    Harness Engineering

    What is it¶

    A harness is the runtime layer that wraps an LLM agent: it handles tool dispatch, context management, safety enforcement, session persistence, and feedback loops — everything that happens after the first prompt. Harness engineering is the discipline of deliberately designing this layer rather than leaving it as scaffolding glue. The term was coined by @mitchellh and synthesized into a playbook by Charlie Guo: "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." The key shift is treating the environment as the primary artifact, not the code the agent produces.

    Distinct from context engineering (what goes in the window), harness engineering is about the surrounding system: constraints, feedback loops, tool design, safety layers, and orchestration protocols. This page asks how much that layer matters next to the model, which of its components earn their cost, and whether harnesses can be designed or optimized systematically rather than by trial and error.

    The short answer: the harness can matter as much as the model, but no single component helps everywhere — the right harness depends on the model, the task and the budget, and it can increasingly be searched for or learned rather than hand-built.

    The harness can matter as much as the model¶

    LLM system performance is heavily determined by harness design, not just model weights. Harness changes alone can produce up to a 6× performance gap on the same benchmark with a fixed model — prior work cited by Meta-Harness, which argues the harness "often matters as much as the model itself." Meta-Harness's own measured gains over hand-designed baselines (below) are consistent with this.

    The practitioner consequence is that the engineer's job splits into two halves (Charlie Guo):

    1. Building the environment — constraints, tools, documentation, feedback loops
    2. Managing the work — planning with agents, reviewing rather than writing code, orchestrating parallel sessions

    These aren't sequential. The agent's failures tell you what the environment is missing; a better environment lets you manage with less friction.

    Separating setup from runtime makes components replaceable¶

    OPENDEV draws a useful line:

    • Scaffolding — assembly before the first prompt: system prompt compilation, tool schema construction, subagent registration. Done once per session.
    • Harness — runtime orchestration: tool dispatch, context compaction, safety enforcement, state persistence across turns. Runs continuously.

    OPENDEV makes this split its organizing principle, so that each component is independently configurable and replaceable. The split is a design description, not a measured result.

    Constraint and feedback increase trust in agent output¶

    Guo synthesizes four recurring practices from OpenAI, Stripe, and Anthropic (Charlie Guo):

    • Architecture as guardrails. Enforce structure mechanically via linters and schemas, not just via instructions. OpenAI enforced a strict layered architecture with rigid dependency rules via custom linters. Stripe ran agents in isolated, pre-warmed "devboxes" with access to 400+ internal tools via MCP servers. The practitioners' counterintuitive lesson: constraining the solution space increased trust in agent output.
    • Tools as feedback. Custom linter error messages double as remediation instructions — the tooling teaches the agent while it works. OpenAI's Greg Brockman, as relayed by Guo, recommends maintaining a list of tools your team relies on and making sure someone takes point on making each agent-accessible (CLI or MCP server).
    • AGENTS.md as living system of record. A Markdown file at repo root, automatically read by agents at session start, updated every time the agent does something wrong. It points to deeper sources of truth (design docs, architecture maps, execution plans) rather than containing everything inline. Background agents can periodically scan for stale docs and open cleanup PRs.
    • Plan before execute. Guo's own advice, which he files under managing the work rather than the harness: agents propose, humans approve, then agents execute. Anthropic's related approach: an initializer agent generates 200+ individual features from a high-level prompt, each with explicit test steps.

    All four come from practitioner reports relayed in one synthesis, not from controlled comparisons. The evidence that executable feedback beats static instructions is covered in Executable Context.

    No component helps every model and task¶

    Most harness comparisons pit complete systems against each other, which can't say which part made the difference. An Empirical Study of Harness Design holds the run loop fixed and varies one component at a time across 176 settings (three Nemotron-3 sizes plus Mistral-Medium-3.5-128B, on SWE-Bench Verified and Terminal-Bench 2.1). No component helps everywhere:

    • Context management pays off mostly by preventing overflow. Its advantage on SWE-Bench falls from 35.7 points at a 32k window to 2.7 at 128k. Cheaply dropping stale tool output before falling back to LLM summarization gives the best cost; making dropped content recoverable adds nothing, because models almost never ask for it back.
    • Planning helps weak models and saves money on strong ones. It adds 11.6 points for the 30B model by keeping runs alive long enough to attempt an edit. For the strongest models it cuts cost about 30% at a 0.4–2.0 point loss, mostly by trimming redundant checking after an edit.
    • Predefined tools help models that are weak at bash. A bash-capable model (Nemotron-3 550B) does better with bash only, +3.6 and +5.6 points at 53% and 30% lower cost, because it combines several operations per call. Mistral prefers the full tool set on SWE-Bench but bash only on Terminal-Bench, so the crossover also depends on the task.

    The authors' conclusion is that each component should be chosen for the model, task type and budget rather than adopted by default. Caveats: every setting was run once, Terminal-Bench has only 89 tasks, and planning and tools were only tested at one context configuration.

    Good harnesses build on what the model already knows¶

    A recurring claim in the practitioner literature is that the harness should be decoupled from any particular model. What is a Harness? gives the clearest anatomy — system prompt, tools, agentic loop, and a translation layer that lets the same harness run different models — and argues the translation layer is what moves leverage from AI labs to end users, who can own, modify, and run the harness locally. Ante is that position as a working artifact: a harness evaluated continuously across model families on Terminal-Bench 2.1 rather than pinned to one hero model, with each result linking a raw audit run and a pinned build. Its comparative efficiency figures are vendor self-reported.

    The practitioner design notes converge on a few principles (Towards a Harness That Can Do Anything):

    • Exploit what the model already knows. Coding and systems administration are overrepresented in training data, so a harness built from familiar primitives costs fewer tokens than one teaching a novel environment. The bash-only result above is a measured case of this.
    • Determinism where possible — the model picks the goal, but deliberation toward it should be well-defined steps.
    • Keep the core prompt small, loading skills into context at runtime rather than preloading them.
    • Feel light to the model, do heavy work underneath — logging, sanity checks, failsafes, sanitization.

    Harness Engineering for Self-Improvement organizes this as an operating-system analogy: encapsulate complicated logic behind a simple interface, and expect configs, tool interfaces, and protocols to standardize across the industry. It also notes the coding-agent loop has already converged across Claude Code, Codex, OpenCode, and Cursor-style agents.

    The surfaces agents act on are part of the harness¶

    Harness design does not stop at the harness. Designing APIs for Agents argues that API design for agents inverts the human-facing defaults: agents read entire documentation sets up front and generate thousands of lines in seconds, so onboarding friction is no longer the cost to minimize — debugging cost is. Concretely: defaults are bad (explicitness is cheap when the consumer fills every field), errors are good (forgiving APIs that coalesce sloppy input produce codebases where different call sites use different values for the same thing), and error messages should tell the agent to read the docs, because modern harnesses will.

    This is the same principle as constraining the solution space, applied one layer out. It is a practitioner argument, not a measured comparison.

    Safety needs independent layers¶

    Production harnesses need defense in depth — a single safety layer is insufficient when agents can execute arbitrary shell commands. OPENDEV describes five independent layers:

    1. Prompt-level guardrails (security policy, action safety)
    2. Schema-level tool restrictions (plan-mode whitelist, per-agent allowed tools)
    3. Runtime approval system (manual/semi-auto/auto with persistent permissions)
    4. Tool-level validation (dangerous pattern blocklist, stale-read detection, timeouts)
    5. Lifecycle hooks (pre-tool blocking, argument mutation)

    Each layer operates independently, so failure of one doesn't compromise the rest. This is one system's design, described rather than evaluated against simpler alternatives.

    Structure can replace generative coordination¶

    Three sources propose structural fixes for long-horizon drift and coordination.

    Procedural Graphs makes procedural knowledge explicit — (procedure, relation, procedure) triplets for what-to-do questions, the way a knowledge graph holds what-is — and translates the active subgraph into step-level guidance that biases the next action without dictating it. The graph self-evolves under a held-out validation gate, which is the detail that distinguishes it from unconstrained self-modification.

    UnitBoost questions a structural assumption in multi-agent harnesses: that the manager must be generative. Replacing it with a defined merge operator — unit map, constrained argmax, explicit residual — makes coordination order-free and provenance-recording, and beats input-matched generative managers. It also states where it does not help: one indivisible unit, unavailable unit identity, or an endpoint charging per emitted unit.

    ICM takes the opposite route for sequential, human-reviewed workflows and drops the orchestration code entirely: numbered folders are stages, a markdown contract in each says what to read and write, and one stage's output folder is the next one's input. Every intermediate state is a file a human can open and edit, so observability comes for free. The authors scope it out of real-time multi-agent work, high concurrency and automated branching, and their evidence is practitioner reports, not controlled comparisons.

    Procedural Graphs is treated in depth under Agent Memory and Retrieval; UnitBoost's place among coordination mechanisms is covered in Multi-Agent Systems.

    Evals belong inside the harness¶

    Anthropic argues evals should be a core component of agent development, not an afterthought. Without them you're "flying blind" — catching issues only in production, where fixing one failure creates others (Demystifying Evals). Two eval categories work together:

    • Capability evals — start low, hill-climb; measure what the agent can do
    • Regression evals — near 100% pass rate; catch backsliding after changes

    Evals also become the highest-bandwidth channel between product and research teams: they define metrics researchers can optimize against. They are also the precondition for the automated optimization below, which needs a score to search against.

    Harnesses can be searched for or learned¶

    Rather than hand-designing harnesses, an outer loop can search over harness configurations automatically. Meta-Harness does this using an agentic proposer with access to source code and full execution traces of all prior candidates. It beats hand-designed baselines in all three domains it tests: +7.7 points over ACE on online text classification with 4× fewer context tokens, +4.7 points on 200 IMO-level math problems across five held-out models, and above Terminus-KIRA on TerminalBench-2 (76.4% vs 74.7% with Opus 4.6). On TerminalBench-2 it searched and evaluated on the same 89 tasks, and another hand-built harness, ForgeCode, still scored higher (81.8%). Existing text optimizers fail here because they compress feedback too aggressively (scalar scores only, no trajectory access).

    Meta-Harness searches afresh for each task. Harness Learning instead trains the reviser, so the skill of revising harnesses carries over to new tasks. A proposer model is trained with RL to edit a frozen solver's harness code from execution reports, rewarded by how the edited harness scores; at test time both models stay frozen and only the harness changes. On 21 Reasoning Gym families unseen in training, mean single-revision score rises from 0.32 to 0.62, and the 4B proposer's average revision beats its 35B teacher's (0.62 vs 0.56). A proposer trained on HotpotQA keeps improving harnesses over ten rounds on MuSiQue and 2WikiMultihopQA. Two details matter for practice: much of the gain is reliability (far fewer edits that break the harness), and training on revision sequences adds nothing consistent over training on single revisions.

    Verification improves when the checker gets the environment¶

    The harness can also be pointed at checking work rather than doing it. VeriHarness turns the generator's own model into a verifier for long-horizon workspace tasks (reports, spreadsheets) by giving it a workspace, evidence tools and reusable verification skills, with no reference answers, rubrics or stronger judge. Across several rollouts, a disagreement resolver checks disputed claims against source files and data, and a consensus challenger tries to refute claims all rollouts share and looks for requirements none of them met. Selection plus evidence-backed revision adds about 6 points over a single rollout with both Gemini 3.5 Flash and Claude Opus 4.8, beating the verification baselines it was compared against. Its verification skills also improve from failure feedback: skills evolved from an empty library beat a human-authored one on held-out tasks.

    The gain comes from the environment, not the model: majority voting and LLM-as-a-judge only re-read what the model already believes. The cost is several full rollouts per task (VeriHarness).

    What the evidence supports¶

    • Treat the harness as a first-class lever. A fixed model can show up to a 6× gap across harnesses (prior work cited by Meta-Harness), and automated harness search beat its hand-designed starting baselines in all three domains Meta-Harness tested — though on TerminalBench-2 it searched and evaluated on the same tasks, and a hand-built harness still scored higher.
    • Choose components per model, task and budget. The one component-level study (Harness Design) finds context management, planning and predefined tools each help some models and hurt or cost others. It ran each setting once, so the direction is more reliable than the magnitudes.
    • Build on primitives the model already knows. Practitioners argue for familiar primitives such as files, logs and the Linux filesystem (Towards a Harness That Can Do Anything); the component study separately measured a bash-capable model doing better and cheaper with bash alone (Harness Design).
    • Give verifiers the environment, not more votes. VeriHarness (VeriHarness) gains about 6 points by checking claims against files and data, where voting and LLM judges cannot add information. It is one paper on workspace tasks.
    • Constraint and mechanical feedback are practitioner advice, not measured. Custom linters, teaching error messages and an approved-plan gate come from one synthesis of practices at OpenAI, Stripe and Anthropic (Charlie Guo).

    In practice¶

    Ordered roughly by evidence strength and cost:

    1. Instrument before you tune. Keep capability and regression evals alongside the harness (Evals belong inside the harness); without a score, neither manual tuning nor automated search has anything to optimize.
    2. Ablate components on your own model and tasks instead of adopting a full-featured harness by default (No component helps every model and task). Try bash-only for strong models, planning for weak ones, and cheap truncation of stale tool output before summarization.
    3. Encode mistakes as mechanical constraints. Each time the agent errs, add a linter rule, schema or teaching error message rather than another instruction, and keep AGENTS.md short and pointing at the checks (Constraint and feedback).
    4. Gate execution on an approved plan for non-trivial work (Constraint and feedback).
    5. Layer safety independently — prompt policy, tool restrictions, approvals, tool-level validation and hooks (Safety needs independent layers).
    6. Choose attended or unattended parallelism deliberately. Attended parallelization — actively managing several sessions, checking in and redirecting — gives more control but is cognitively demanding. Unattended parallelization (Stripe's "Minions") — post a task, walk away, let CI carry it, re-enter at review — scales better but needs substantially more harness investment up front (Charlie Guo).

    Open questions¶

    • How do you keep agent-written code from accumulating entropy? Agent-generated code accumulates cruft differently than human-written code; "garbage collection" agents are an emerging practice but not yet mature (Charlie Guo). A longitudinal comparison of codebases with and without them would settle whether they work.
    • Does any of this retrofit onto brownfield codebases? The success stories Guo surveys all involve greenfield projects (Charlie Guo). No source reports applying these practices to a large existing codebase.
    • Is environment-backed verification affordable outside benchmarks? Agents mark features complete without proper end-to-end testing (Charlie Guo). VeriHarness shows a same-model verifier with environment access helps on workspace tasks, but at the cost of several full rollouts per task (its released pool cost over $100,000) (VeriHarness). A cost-matched comparison against cheaper checks would answer it.
    • Search per task, or learn to revise? Meta-Harness optimizes each task from scratch; Harness Learning trains a reusable reviser that transfers. No source compares them on the same tasks at matched cost (Harness Learning).
    • What does organizational adoption take? None of this happens by accident; the practices require deliberate organizational adoption (Charlie Guo), and no source studies what makes it stick.
