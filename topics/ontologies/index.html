    Ontologies

    What is it¶

    An ontology is a formal representation of entities, their properties, and the relationships between them within a domain. In the context of LLMs and AI systems, ontologies matter because they provide the structured semantic layer that language models lack — bridging the gap between natural language understanding and precise, relational reasoning.

    The literature reveals a recurring pattern: LLMs are powerful pattern matchers over text but struggle with tasks requiring explicit relational structure. Knowledge graphs, schemas, taxonomies, and other ontological representations often improve LLM performance when the task demands understanding how things relate to each other rather than just what things are (KG Benchmark, GraphRAG Survey) — though how the structure is delivered matters, and injecting it badly can hurt.

    This page covers why LLMs benefit from explicit structure, how fixed and emergent ontologies trade off, and — at most length — how to build an ontology layer for an agent and keep it from rotting. Structured context in general is Context Engineering; self-organizing memory structures are Agent Memory and Retrieval.

    The short answer: explicit structure helps relational reasoning when it is queried rather than injected, but an agent ontology is only worth what its maintenance is — it can decay within weeks unless definitions change with the data, entries are grounded in the data, and every change is gated on behaviour.

    Explicit structure lifts relational reasoning¶

    LLMs encode knowledge implicitly in weights, but this representation has fundamental limits for structured reasoning. The enterprise QA benchmark demonstrates this starkly: GPT-4 (zero-shot, 43 questions) achieves only 16.7% accuracy on direct SQL queries over a 13-table subset of a 199-table insurance schema, but 54.2% when given a knowledge graph representation of the same data — a 37.5 percentage point gain (KG Benchmark). The missing ingredient is a "contextual ontology layer" — business semantics that map domain concepts to database structures.

    This gap shows up across domains. Standard RAG treats documents as flat text and struggles with relational queries; GraphRAG captures entity relationships explicitly and enables multi-hop reasoning that flat retrieval cannot (GraphRAG Survey). Knowledge graph QA requires bridging the "semantic gap" between natural language and structured representations — queries and graphs organize information differently, and EoG addresses this with a parse→prune→enrich pipeline (EoG).

    The KG benchmark is a single controlled comparison on one schema; the GraphRAG evidence is a survey. The direction is consistent, the magnitude is one data point.

    Models hold implicit structure, but it is opaque¶

    LLMs do possess internal ontological structure — it's just opaque. MLP weights behave like key-value memories that editing methods target, though the survey stresses that knowledge is distributed and entangled across parameters and layers, and that localization methods are contested (Knowledge Editing). The theoretical mechanism for this is now better understood: in-context learning works by converting input context into an implicit rank-1 weight update on MLP layers — a form of weight editing at inference time without gradient updates (Learning Without Training). Read together, these two sources suggest a common lens on steering vectors, knowledge editing, and ICL — all as manipulations of the same implicit key-value memory. That is this page's synthesis and a theoretical link, not an empirical one; the Learning Without Training result is shown for a single contextual block.

    If the lens holds, adding structured context (a knowledge graph, a schema) amounts to editing the model's working knowledge for that inference. External ontological structure and internal implicit structure are complementary, not competing.

    Fixed ontologies are precise, emergent ones adapt¶

    A key tension in the literature is between predefined and emergent ontological structures.

    Fixed ontologies — knowledge graphs, database schemas, taxonomies — provide precision and consistency but are brittle. They require upfront design, struggle with novel entities, and can't adapt when the world changes. AgREE shows that standard KG completion methods fail for genuinely emerging entities (new startups, public figures) because they assume entities already have some graph representation (AgREE). A-MEM argues that memory systems' "reliance on predefined schemas and relationships fundamentally limits their adaptability" (A-MEM).

    Emergent ontologies — structures that self-organize from data — trade precision for adaptability. A-MEM uses Zettelkasten-style principles to let memories form interconnected networks dynamically, with new memories triggering updates to existing ones (A-MEM). EverMemOS consolidates episodic memory traces into thematic "MemScenes" with stable semantic structures that evolve over time, mirroring human memory consolidation (EverMemOS). These approaches let the ontology emerge from usage rather than requiring it to be specified upfront. Both are covered as memory architectures in Agent Memory and Retrieval.

    The practical sweet spot may be hybrid: use formal ontologies where the domain is well-understood and stable, but allow emergent structure at the edges where novelty appears.

    Ontological operations may have a small algebraic basis¶

    Category theory offers a rigorous framework for thinking about ontological transformations. The relational core of a dataframe algebra decomposes into three migration functors (Delta, Sigma, Pi) plus two topos operations for set-style operations such as DIFFERENCE and DROP DUPLICATES, and encoding these in a type system allows compile-time verification of every schema transition (Category Theory & Dataframes). This matters because it suggests that ontological operations — mapping between different representations of the same domain — have a small, well-defined algebraic basis.

    The learning-without-training result is a parallel insight at the model level: in-context learning decomposes into a rank-1 weight update plus a steering vector — a similarly compact basis for what appears to be complex adaptive behavior (Learning Without Training). Both results point toward underlying structure being simpler and more decomposable than it appears. This is a theoretical parallel drawn on this page, not a tested claim.

    Agent ontologies decay fast, and raw access doesn't substitute for them¶

    The sections above argue that agents need external semantic structure. A newer cluster of sources — one research system, several production reports from data and engineering teams, and work on self-evolving context — addresses the practical question: how to build such a layer for an agent, and how to stop it rotting. The sources converge to a striking degree, even though most never use the word "ontology".

    Decay is fast and measurable. Anthropic's analytics agent reached ~95% accuracy with curated reference docs, then drifted to ~65% within one month when those docs fell out of sync with the data models (Anthropic Analytics). Meta's tribal-knowledge project puts the stakes plainly: "context that decays is worse than no context at all" (Meta Tribal Knowledge). Notion found that a query can run cleanly and still answer the wrong question, because the meaning, routing, measurement or interpretation went wrong. Its conclusion: "curated context is as important as the connection itself", and that knowledge "needs an owner and a way to stay current" (Notion Data Scout).

    Curation also beats raw access by a wide margin. In Anthropic's case, curated skills moved accuracy from 21% to 95%+, while giving the agent grep access to thousands of historical SQL queries moved it by less than one point (Anthropic Analytics). In Anthropic's case, raw access to prior queries was no substitute for curation.

    Good entries are scoped by the workload and grounded in the data¶

    The construction practices the sources converge on:

    • Scope from the workload, not the domain. EvoOntology's builder agent proposes candidate concepts from the recurring entities, metrics and conditions in real questions, then probes the data to verify each one (EvoOntology). Notion's advice is to start with a small set of recurring questions "rather than trying to document the entire company first" (Notion Data Scout).
    • Ground every entry in the data, with evidence. In EvoOntology's ablation, Mappings (term → exact columns and join paths) and Evidence (probe-query results) carry most of the weight: removing them costs 13.4 and 8.7 points, against 3.5 for Constraints and 2.1 for Relations. Entries are committed only when a probe verifies them, never on a prose description alone (EvoOntology). GroundedKG-RAG applies the same principle to text: every node and edge stays anchored to source spans rather than to LLM-generated summaries (GroundedKG-RAG).
    • Point to the canonical source; don't copy it. Notion's index entries reference the maintained definition instead of duplicating it (Notion Data Scout). The "Hidden Flaw" critique explains why: LLM-authored copies become "borrowed correctness" that drifts undetectably as the system turns self-referential (Hidden Flaw).
    • Separate concerns so they can change independently. Notion splits data context (how to calculate), business context (how to interpret) and routing guidance (which source to use). EvoOntology splits content, schema and tool layers, and gives the content layer typed node families: Terms, Mappings, Constraints, Evidence (Notion Data Scout, EvoOntology).
    • Use typed relationships that encode lifecycle. supersedes, depends-on and owned-by make staleness traceable: when a definition changes, its dependents are known (LLM Wiki v2). STALE shows why this has to happen when an entry is written rather than at query time. In the strongest memory framework it tested, the old entry was among the top three recalled 60.5% of the time when new evidence arrived, yet only 3.3% of those old entries were flagged for update. Stale and current entries then coexist, and retrieval alone does not decide which is authoritative. The authors' prototype marks entries active or stale on write and propagates changes to dependent attributes, which raised accuracy from 8.7% to 68.0% on the same model (STALE).
    • Let LLMs draft; let humans own the definitions. Anthropic tried bootstrapping its semantic layer by having an LLM generate metric definitions from raw tables and query logs. It "produced plausible-looking definitions that encoded the very ambiguities we were trying to eliminate, and was net-negative on our evals versus a smaller, human-curated layer." Their rule now: Claude writes the documentation, a human owns the definition (Anthropic Analytics). The Library Drift authors cite a similar gap for skills: LLM-authored skills +0.0pp versus +16.2pp for human-curated ones on SkillsBench (Library Drift). The counterpoint is dbt's benchmark: an LLM created three dbt models that brought all 11 benchmark questions into semantic-layer coverage, where accuracy reached 98–100%. That is a small, vendor-run test (dbt 2026 Benchmark). The difference appears to be whether LLM output is checked before it becomes the definition.
    • Keep entries short. Meta's "compass, not encyclopedia" files are 25–35 lines (~1,000 tokens) each, about 59K tokens for all 59 (the secondhand summary's claim of under 0.1% of a context window doesn't match its own figures) (Meta Tribal Knowledge).

    Query the ontology; don't inject it¶

    How the ontology reaches the agent matters as much as its content (see Context Engineering). In EvoOntology, prepending the semantic layer to the prompt sometimes hurt (−15.0 Traj-Wise for one backbone; up to −5.6 EX on BIRD). Serving the same content through MCP browse/resolve tools produced +17.8 Traj-Wise on average. A static fragment "competes with the agent's other instructions and cannot be pruned per turn" (EvoOntology). The production designs agree:

    • Codified Context keeps a small always-loaded core and fetches its cold specification documents on demand (Codified Context).
    • Notion uses database properties to find entries and page bodies to hold them. Packing guidance into properties overloaded the metadata and was harder to maintain (Notion Data Scout).

    The interface is also where improvement concentrates. In EvoOntology, tool-layer edits — changes to how content is exposed — produced 57% of the evolution gain, even though content edits ran in nearly twice as many rounds (11 vs 6) (EvoOntology).

    Drift is prevented at the point of change and caught by behavioural gates¶

    The sources describe two complementary mechanisms: prevent drift at the point of change, and detect and repair what still slips through.

    Prevention¶

    • Change the definitions with the data. Anthropic's response to its 95% → 65% drift was to keep skill docs next to the data models and update them in the same PRs. A code-review hook flags any reporting-model change that doesn't touch a skill file. About 90% of data-model PRs now include a skill change, and Anthropic reports aggregate accuracy of ~95% (self-reported; no post-fix time series published) (Anthropic Analytics). This is the only maintenance practice in the wiki tied to a reported before/after. dbt's benchmark shows a comparable mechanism: its semantic layer updated automatically when models were pushed to git, while text-to-SQL context had to be updated separately (dbt 2026 Benchmark).
    • Validate references mechanically. Meta's maintenance agents check that every file path still resolves, find coverage gaps and fix stale references (Meta Tribal Knowledge). The same check applies to the tables, columns and join paths an ontology names.
    • Give every entry an owner and a freshness date. LLM Wiki v2 records verification dates and responsible parties, and its audits assign trust scores that decay without re-verification (LLM Wiki v2).

    Detection and repair¶

    • Harvest corrections into patches and evals at the same time. Anthropic's scheduled agent scans stakeholder channels every few hours for correction language. It drafts a one-line fix to the relevant reference doc and opens a PR tagged to the domain owner. The same corrections feed the offline eval set, so each fix also becomes a regression test (Anthropic Analytics). This is the production form of a failure-driven loop: the agent proposes, the owner merges.
    • Let agent failures drive updates. EvoOntology mines agent trajectories for recurring failure signatures and attributes each one to the content, tool or schema layer before patching. Skipping attribution costs 6.3 points (EvoOntology). Notion runs a nightly review agent over conversations, Slack, Notion and GitHub to find missing, stale or conflicting context (Notion Data Scout). SkillX also expands coverage deliberately toward failure-prone and under-used areas (SkillX).
    • Make small additions, not rewrites. ACE identifies context collapse (iterative rewriting erodes detail) and brevity bias (updates drift toward generic summaries) as the failure modes of self-maintained context, and counters them with structured incremental deltas (ACE). EvoOntology's patches likewise touch only one layer at a time (EvoOntology).
    • Gate every change on behaviour, not just validity. This is the most important element of the repair loop. EvoOntology accepts a candidate only if it beats its parent by a margin on a held-out validation set; removing the gate costs 11.2 points, because "unfiltered candidates admit regressions that the next round cannot always undo". Rejected candidates are logged so the same bad fix is not proposed again (EvoOntology). Agent Plasticity suggests why a structural check is not enough: in its failure analysis (observational), agents sometimes failed to use relevant persistent artifacts, or failed while using them. Its authors conclude that validation "should assess their behavioral effectiveness, not only whether they are structurally valid or executable" (Agent Plasticity).
    • Don't let agents change definitions unreviewed. Small mechanical fixes can be automated — Notion's triage agent applies small, well-supported fixes and Meta auto-fixes stale path references — but agents are unreliable maintainers of meaning:
    • Repo2Skill-Evo shows that skills go stale silently after a release: they still load and get retrieved, but give obsolete guidance with no error. Its 105 transitions across 57 repositories were deliberately selected because the releases affect skills, so this shows how silent staleness is, not how often it happens. Asked to update the skills from the release patch, six frontier agents reach only 29.9–69.7% macro F1, failing through incomplete coverage or overbroad edits (Repo2Skill-Evo).
    • On STALE, a benchmark of a personal assistant's memory of a user, the best model reaches 55.2% at recognising and acting on memories that later evidence has implicitly invalidated. Models that correctly call a belief outdated when asked still go along with queries that presuppose it (STALE). The domain is user state rather than data definitions, but the failure transfers.
    • Treat signals as evidence, not authority. Notion's triage agent applies only small, well-supported fixes and escalates anything ambiguous to the owner. Its rules: "evidence isn't approval", "merged isn't deployed", preserve newer human edits. The answering agent never rewrites its own definitions mid-answer (Notion Data Scout). Everything is Context builds the same role separation into its architecture, with humans as curators and verifiers (Everything is Context).
    • Trace which definitions each answer used. Notion tags every query with the metric, definition, filters and time window, so a wrong answer can be attributed to the definition, the routing or the execution. Its authors are explicit that query success and rising usage do not prove accuracy; validation against answers confirmed by the data owners is still in progress (Notion Data Scout).

    Keeping the eval set current¶

    The gate is only as good as the eval set behind it, and that set goes stale too. Anthropic's practices are the most concrete in the wiki (Anthropic Analytics):

    • Pin ground truth so it can't drift. Fix each eval to a snapshot date or a stable fact table, or grade the agent's query rather than its number.
    • Rerun affected evals in CI whenever a PR touches one of their dependencies.
    • Grow the set from corrections. Every stakeholder correction is a candidate eval.
    • Store results like telemetry. Record skill version, git SHA and model ID with each run, so slow regressions show up as a time series.
    • Gate launches per domain. A domain owner's eval slice must clear a threshold (initially ~90%) before that domain goes live.
    • Don't over-collect. Returns diminish "past a few dozen per topic", and that ceiling drops with each model generation.

    Health signals¶

    • Convergence. A well-behaved evolving ontology converges. EvoOntology's content growth concentrates in the first three rounds, then falls below 5% per round as performance plateaus (EvoOntology).
    • Size as an overfitting signal. Sustained growth suggests bloat rather than learning. Anthropic stopped refining docs after "three consecutive net-negative iterations: the docs were getting longer, not better" (Anthropic Analytics). Amazon's work on research agents gives the mechanism: a strategy that fits in a few tokens cannot have memorised its validation set, and compressing a strategy into a short prompt separates genuine gains from overfitted ones (Amazon: Why Agents Don't Overfit).
    • Watch per-entry signals, not just end metrics. In Library Drift's experiments, an over-aggressively governed library fell below the no-skill baseline, and the authors argue ungoverned ones can too. Aggressive retirement collapsed one library to two active skills while end-task accuracy declined only gradually. Per-skill contribution scores and engagement rates exposed the drift before the headline metric moved (Library Drift).
    • Model changes are a decay source of their own. An evolved ontology is tuned to its model: moving it to a different backbone costs 6.6–10.9 points (EvoOntology). Anthropic logs the model ID with every eval run and regularly prunes skill scaffolding as models improve (Anthropic Analytics). Re-validate whenever the model changes, even if the data hasn't.

    The case for an ontology is meaning, not performance¶

    MotherDuck argues that the classic semantic layer was a 1990s workaround for slow databases, and that it created a priesthood of specialists instead of democratizing data (Who Needs a Semantic Layer). The agent-era sources do not contradict the history so much as change the justification. The case is no longer performance; it is meaning — which definition to trust, and how to interpret a number. Even so, the warning applies: an ontology that only specialists can maintain will decay. Both Anthropic's colocation (Anthropic Analytics) and Notion's choice of a familiar editing surface (Notion Data Scout) are, in part, answers to that.

    What the evidence supports¶

    • Explicit structure helps when the task is relational. The KG benchmark's 16.7% → 54.2% (zero-shot GPT-4, 43 questions, KG Benchmark) and the GraphRAG survey (GraphRAG Survey) point the same way, though the magnitude rests on one controlled comparison.
    • Curation beats raw access, and decays fast. Anthropic's curated skills took accuracy from 21% to 95%+ where grep over historical queries added under a point, then drifted to ~65% within a month when docs fell out of sync. Both figures are self-reported, from one team (Anthropic Analytics).
    • Deliver through tools, not the prompt. EvoOntology measured prompt injection sometimes hurting and tool-based access adding +17.8 on average on DDR-Bench, against plain ReAct; the production designs agree. One research system, on benchmarks (EvoOntology).
    • Gate changes on behaviour, and keep humans owning definitions. Removing EvoOntology's held-out gate cost 11.2 points (EvoOntology); LLM-drafted definitions were net-negative at Anthropic (Anthropic Analytics); agents updating skills from a release patch reach only 30–70% macro F1 (Repo2Skill-Evo), and the best model recognises invalidated memories only 55% of the time (STALE). No source lets an agent change definitions autonomously in production.
    • Colocating definitions with the data is the best-supported practice in production. It is the only one with a reported production before/after (Anthropic, self-reported, no post-fix time series; Anthropic Analytics); the behavioural gate's support is a benchmark ablation.

    The limits are clear. The quantitative construction and evolution results come from one research system, which also has internal inconsistencies noted on its source page. The production accounts (Anthropic, Notion, Meta) are self-reported, with little or no controlled evaluation. Only Anthropic reports measured decay, and only over one month. No source follows any agent ontology, curated or evolved, over many months. The long-run risks of gated loops are visible in the sources: bloat (Anthropic's docs "getting longer, not better", Anthropic Analytics), pruning collapse (Library Drift), and self-attribution loops that reliably find fixes but are blind to regressions (Agentic Harness Engineering). Validation overfitting is the remaining risk; Amazon's compression argument is one guard against it.

    In practice¶

    1. Start from a few recurring questions, not the whole domain, and commit only entries a probe query verifies (Good entries are scoped by the workload).
    2. Serve the ontology through tools (browse/resolve) rather than pasting it into the prompt (Query the ontology).
    3. Keep definitions next to the data models and update them in the same pull requests, with a review hook that flags model changes that don't touch a definition (Prevention).
    4. Harvest corrections into patches and evals together, gate every change on a held-out eval, and route changes to meaning to a human owner (Detection and repair).
    5. Pin the eval set's ground truth and log skill version, git SHA and model ID with each run (Keeping the eval set current).
    6. Watch size and per-entry signals, and re-validate whenever the model changes (Health signals).

    Open questions¶

    • Can LLMs bootstrap useful ontologies from unstructured text? Or do they hallucinate plausible-looking but unreliable structure? EvoOntology's answer is to commit only probe-verified entries, but this has only been tested on benchmark data.
    • Does the alignment problem get easier or harder with scale? As knowledge graphs grow, the semantic gap between NL and graph structure could narrow (more context) or widen (more ambiguity). No source measures it.
    • How do ontologies behave over months? The mechanisms are now well described: colocated updates, mechanical reference checks, failure-driven patches, behavioural gates. What is missing is longitudinal evidence. Does a gated self-evolving ontology stay stable, or accumulate drift that held-out sets miss? A falsifiable test would compare a human-gated loop with an autonomously gated one on the same data estate, over N months and K model changes, against a holdout neither loop touches. A deep-research note of 2026-10-09 (not a source page) tested this and found the evidence inconclusive.
    • Can one bad correction poison both the ontology and its gate? Correction harvesting feeds the same Slack message into both the patch and the eval set, so one bad correction contaminates the artifact and its gate together. No source examines this path.
    • How should genuinely new concepts enter? AgREE's agentic KG completion for emerging entities is the main lead; none of the maintenance loops above handles them explicitly.
    • When is implicit knowledge enough? The rank-1 update framework suggests that context injection is equivalent to a lightweight knowledge edit. When to rely on this implicit mechanism vs. explicit graph structure is untested.
